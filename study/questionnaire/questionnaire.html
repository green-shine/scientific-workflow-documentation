Key Workflow Steps

  • Defines a Snakemake workflow module named spilterlize_integrate with a minimum Snakemake version requirement, report generation, and project configuration loading.

Workflow Overview

This workflow supports exploratory preprocessing and comparison of count-based datasets across biologically or technically defined sample subsets. Based on a sample annotation table, it can generate analyses for the full dataset and for configured splits, then produce visual outputs for raw counts, filtered data, multiple normalization variants, optional batch-effect–integrated data, and highly variable feature selections. It is useful in projects that need to assess how normalization and integration choices affect downstream structure and clustering across different sample groups. Researchers working with annotated count matrices, especially those comparing preprocessing strategies or examining batch-corrected versus uncorrected representations, would benefit from this workflow’s organized production of summary plots, clustered heatmaps, and associated exported configurations and environments.

Technical Documentation: genome_tracks Snakemake Workflow

1. Purpose

This workflow defines a Snakemake module named genome_tracks for generating genome track visualizations and browser-compatible track assets from a set of genomic samples and target loci. The workflow reads project configuration, sample annotations, and a gene/region list, resolves target genomic intervals, and delegates processing to additional included rule files. Its final targets include per-gene track images, UCSC track hub metadata, exported Conda environments, and archived configuration files.

2. Workflow Overview

Module identity

  • Module name: genome_tracks
  • Minimum Snakemake version: 8.20.1
  • Workflow report path: report/workflow.rst
  • Primary config file: config/config.yaml

3.2 Sample annotation table

The workflow loads the sample annotation sheet with:

annot = pd.read_csv(config['sample_annotation'])

This table must contain at least:

  • bam
  • group

group column behavior

The group field supports two modes:

  1. Direct group label If group does not end with .tsv, it is treated as a regular visualization group label.
  2. Single-cell metadata file If group ends with .tsv, the file is interpreted as a per-cell metadata table. The workflow reads the second column ([1]) and extracts unique group values from it.

This design allows the workflow to support both bulk/grouped samples and single-cell BAMs with group assignments stored externally.

3.3 Gene list table

The workflow loads the gene list using:

gene_dict = pd.read_csv(config['gene_list'], index_col="gene_region").to_dict('index') genes = list(gene_dict.keys())

Therefore, the gene list CSV must contain:

  • a column named gene_region, used as the index
  • a column named ymax, used during annotation assembly

Supported gene_region values

Each gene_region entry can be either:

  • a genomic coordinate string matching chr[0-9XY]+:[0-9]+-[0-9]+
  • a gene symbol or gene identifier resolvable by parse_gene()

4. Internal Data Processing Logic

4.1 Single-cell group extraction

The workflow builds a dictionary of single-cell sample metadata keyed by an MD5 hash of the BAM path:

bam_hash = hashlib.md5(row['bam'].encode()).hexdigest()

Each entry stores:

  • the BAM path
  • the metadata TSV path
  • the unique group names extracted from column 2 of the TSV file

Why hashing is used

The BAM path hash serves as a stable unique key for each single-cell sample. This avoids collisions that could happen if file basenames are reused. That rationale is inferred from the implementation comment and key structure.

Derived grouping variables

The workflow derives:

  • sc_groups: unique groups across all single-cell metadata files
  • plot_groups: union of sc_groups and all non-TSV group labels from the annotation table, sorted lexicographically

This means the workflow normalizes group definitions from two different sources into a single set of plotting groups.

4.2 Result path construction

All module outputs are rooted under:

result_path = os.path.join(config["result_path"], module_name)

So the effective output directory is:

<result_path_from_config>/genome_tracks/

4.3 Target gene/region resolution

The workflow processes each requested gene_region entry as follows:

  1. If the entry matches the genomic coordinate regex, it is parsed with parse_region(...).
  2. Otherwise, it is resolved as a gene using parse_gene(...).
  3. If parse_gene(...) returns -1, the gene is marked for removal.
  4. For successfully resolved entries, the result is combined with that row’s ymax value and appended to gene_annot_list.

Important dependency

The functions parse_region() and parse_gene() are not defined in the visible Snakefile. They are likely provided by one of the included rule or helper files, most plausibly rules/common.smk, but that cannot be confirmed from the uploaded file alone.

Handling unresolved genes

If one or more genes cannot be resolved:

  • the workflow creates the module result directory if needed
  • writes them to: genes_not_found.csv
  • removes them from the active target list before downstream expansion

This prevents failed symbol resolution from breaking all downstream outputs.

4.4 Normalized gene identifiers

After resolution, the workflow transforms gene labels by replacing : with -:

genes = [gene.replace(':', '-') for gene in genes]

This is likely done to make region-style identifiers safe for filenames.

The final resolved annotation table is then stored in memory as:

gene_annot_df = pd.DataFrame( gene_annot_list, columns=['chr', 'start', 'end', 'count', 'ymax'], index=genes )

Note on count

The meaning of the count field is not defined in the visible Snakefile. It is presumably returned by parse_region() or parse_gene() and used by downstream visualization rules. That is an inference, not an explicit statement in the file.

9. Operational Notes

9.1 Coordinate format restrictions

The coordinate regex only accepts chromosome strings of the form:

chr[0-9XY]+:[start]-[end]

This means it may not match:

  • mitochondrial contigs like chrM
  • alternative contigs
  • lower-case chromosome names
  • non-human naming conventions such as 1:100-200 without chr prefix

This is important for portability across genome builds and organisms.

9.2 Sample metadata TSV assumptions

For single-cell grouping files, the workflow assumes:

  • tab-separated format
  • no header
  • group labels stored in the second column (index 1)

If the file format differs, grouping extraction will fail or produce incorrect results.

9.3 Missing-gene behavior

Unresolvable gene symbols do not stop the workflow globally. Instead, they are logged to genes_not_found.csv and excluded from downstream target generation.

This improves robustness for partially outdated or mixed gene lists.

Workflow Overview

By combining sample annotations, a user-provided gene/region list, and genome-based coordinate resolution, the workflow organizes per-locus track outputs, prepares a UCSC track hub, and records unresolved gene entries. It is relevant for researchers who need shareable genome-browser views and project-specific track figures for comparative analysis across sample groups.

CQN and VOOM activation depend on empty-string checks, which is simple but brittle if config values are malformed.

  1. Integration naming assumes normalized method labels

The workflow prepends norm during integration output generation, so config values in removeBatchEffect_parameters.norm_methods must align with that convention.

4.1 Single-cell group extraction

Each entry stores:

The BAM path hash serves as a stable unique key for each single-cell sample. This avoids collisions that could happen if file basenames are reused. That rationale is inferred from the implementation comment and key structure.

Derived grouping variables

  • plot_groups: union of sc_groups and all non-TSV group labels from the annotation table, sorted lexicographically

This means the workflow normalizes group definitions from two different sources into a single set of plotting groups.
